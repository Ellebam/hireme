## Architect Re-Plan (2026-02-15) — Schema Disambiguation Fix

### Problem Analysis

The QA-blocking issue is a **JSON Schema `oneOf` collision** in the backend validator. When a new certifications or projects section is added, the frontend creates default content `{ entries: [] }`. The backend schema uses `oneOf` to validate section content, but `{ entries: [] }` matches **7 different content schemas simultaneously** because empty arrays skip `items` validation:

| oneOf Index | Schema | Required | Matches `{ entries: [] }`? |
|-------------|--------|----------|---------------------------|
| 2 | experienceContent | `["entries"]` | YES |
| 3 | educationContent | `["entries"]` | YES |
| 5 | languagesContent | `["entries"]` | YES |
| 6 | certificationsContent | `["entries"]` | YES |
| 7 | projectsContent | `["entries"]` | YES |
| 8 | awardsContent | `["entries"]` | YES |
| 9 | publicationsContent | `["entries"]` | YES |

`oneOf` requires **exactly one** match. Seven matches = validation failure.

**Why this wasn't caught before:** Existing sections (experience, education, etc.) are seeded with populated entries, so their item-level `required` fields disambiguate them. The collision only surfaces when adding a **new, empty** entry-based section — which T-011/012 introduced for the first time.

**This is a latent bug affecting all 7 entry-based types**, not just certifications/projects. If a user deleted all entries from their Experience section, the same collision would occur on save.

### Decision: Schema Discrimination Strategy

**Decision 1: How to disambiguate section content in JSON Schema?**

- **Option A: `if/then` conditioned on `section.type` field** — Replace `oneOf` on `content` with `if/then/else` blocks in an `allOf` array. Each block checks `type` (e.g., `"certifications"`) and constrains `content` to the matching schema. Uses the existing `type` field as a discriminator.
  - Pros: No new data fields, no migration, no frontend changes, standard JSON Schema 2020-12 pattern, future-proof
  - Cons: Schema becomes more verbose

- **Option B: Add `contentType` discriminator to each content object** — Add `"contentType": { "const": "certifications" }` to each content schema.
  - Pros: Explicit discrimination
  - Cons: Requires data migration for all existing CVs, TypeScript type changes, Go struct changes, seed data changes, massive blast radius

- **Option C: Frontend workaround** — Never save empty entries (pre-populate dummy entries or defer save until first entry added)
  - Pros: No schema changes
  - Cons: Hack, latent bug remains, UX degradation

**Choice: Option A** — **Rationale:** Zero data migration, zero frontend changes, zero Go struct changes. The `type` field is already a perfect discriminator that exists on every section. The Go validator library (`santhosh-tekuri/jsonschema/v5 v5.3.1`) fully supports `if/then/else` and `allOf` per JSON Schema 2020-12 spec.

### Schema Change Design

Replace the `oneOf` in section `content` with `if/then` blocks conditioned on the `type` property:

**Before (broken):**
```json
"content": {
  "oneOf": [
    { "$ref": "#/$defs/personalContent" },
    { "$ref": "#/$defs/experienceContent" },
    ...
  ]
}
```

**After (fixed):**
```json
"content": { "type": "object" },
...
"allOf": [
  {
    "if": { "properties": { "type": { "const": "personal" } }, "required": ["type"] },
    "then": { "properties": { "content": { "$ref": "#/$defs/personalContent" } } }
  },
  {
    "if": { "properties": { "type": { "const": "certifications" } }, "required": ["type"] },
    "then": { "properties": { "content": { "$ref": "#/$defs/certificationsContent" } } }
  },
  ... (12 blocks total, one per section type)
]
```

The `allOf` array lives at the `section` level (sibling to `properties`), not inside `content`. Each `if` block checks if the section's `type` field matches a specific value, and if so, the `then` block constrains `content` to the correct schema.
